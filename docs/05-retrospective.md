# 05 复盘与改进方向

## 做得好的地方

1. **防虚报设计是本项目最有价值的决策**。让模型只输出"选哪个动作"，最终结论一律由工具观察结果推导（`build_final_result`），从机制上杜绝了"声称已发布/谎报保存成功"——这不是靠 prompt 求模型别撒谎，而是让谎话无法进入结果结构。
2. **Mock/真实双路径**让全部验收点离线可复现、测试确定性可断言，同时用真实模型验证了流程的普适性，不依赖"模型恰好配合"。
3. **真实模型测试暴露了单测测不出的缺陷**（幂等键绕过路径）。mock 的确定性策略永远不会想到"换一个替代时段重存"，只有真模型会走出这条路径。工具级幂等 + 验收断言（drafts.json 记录数）抓住了它。
4. **失败路径显式建模**：保存失败、素材不存在、步数超限都有明确的状态与原因字段，而不是笼统的 error。

## 遇到的坑

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 真实模型首跑全军覆没（steps=0） | `urlopen(req=...)` 参数名笔误 | 修复；教训：LLM 层也要有冒烟测试，单测全绿不代表网络路径可用 |
| 同素材产生两份草稿 | 幂等键含"保存时段"，换替代时段即绕过 | 幂等键改为"原始要求时段"，语义对齐验收点 |
| 结果误判 no_risk | 结果推导未感知必填字段规则 | 把规则传入结果推导，缺字段独立分支 |
| API 429 限流 | 网关限流 + 重试不足 | 递增退避重试 |
| Windows 控制台 GBK vs UTF-8 | 中文输出乱码 | CLI 启动时 reconfigure stdout，文件一律 UTF-8 显式编码 |

## 已知限制

1. **日期/时段校验较宽松**：未强校验时间必须是合法整点、日期必须是未来；依赖工具层宽松接受，生产环境应加输入校验。
2. **草稿存储为 JSON 文件**：无并发锁，多进程同时写会互相覆盖；生产应换数据库或加文件锁。
3. **query_slot 不反映已保存草稿**：草稿尚未进入 `existing_schedule.json`，时段查询只看已有排期。靠 save_draft 的幂等与占用拒绝兜底，但两个并发任务可能保存到同一时段——需要"确认"环节落到正式排期表才能彻底解决。
4. **MockLLM 是策略脚本不是模型**：它验证的是 Agent 框架的正确性，不能证明真实模型永远遵守边界；真实模型路径目前只在 5 个场景验证过。
5. **无鉴权/多用户概念**：草稿确认、审批流程都是题设简化，实际系统需要操作人与审批流。

## 如果继续迭代

1. **草稿确认闭环**：增加 confirm_draft 工具与"确认后进入正式排期"状态迁移，让 query_slot 能看到待确认草稿（预占用提示）；
2. **多素材批量模式**：扫描全部待处理素材，输出每日排期建议清单（题目 CLI 已预留 --scan 入口）；
3. **结构化评测集**：把 examples 的断言固化为独立评测脚本（JSON 断言而非打印），接入 CI；
4. **真实模型行为回归**：对关键验收点用真模型跑固定 seed/temperature=0 的回归集，观察提示词改动的影响；
5. **可观测性**：每次运行的 token 消耗、工具调用耗时统计，便于成本评估。

## 一点感受

Agent 的难点不在"让模型动起来"，而在**让失败可见、让边界不可绕过**：步数上限、幂等、失败显式返回、结论接地，这些机制比提示词更可靠。真模型测试是必须的——它会走你意想不到的路径。
